# FraudShield Model Card

**Model**: XGBoost binary classifier (primary) + Isolation Forest (secondary, AI-4)
**Version**: xgboost-v1
**Training data**: Synthetic — 5,000 rows, seed 42, 12% fraud prevalence
**Train/test split**: Out-of-time — train on `txn_ts < 2026-01-01+05:30`, test on `txn_ts >= 2026-01-01+05:30`
**Intended use**: Internal fraud-risk scoring, invoked by Spring Boot during transaction authorisation
**Prohibited use**: Must not replace human review; must not be used in production without real labelled data validation

---

## 1. Scope and Limitations

This model is trained exclusively on **synthetic data** generated by a controlled logit function. Its outputs:

- Are representative of the model's _architecture and feature set_ only
- Must not be interpreted as production fraud-detection accuracy
- Require recalibration and evaluation on real transaction data before any production deployment

The model does not process, store, or expose full PAN numbers. Only the 15 document-defined features are used; `txn_id`, `txn_ts`, and `city_tier` are excluded from model input.

---

## 2. Operating Threshold — Rationale and Cost Analysis (AI-3)

### 2.1 Cost Model

The threshold was selected by minimising the expected cost function on the **validation period** (never the test period):

```
Cost(theta) = SUM_{i in FN(theta)} amount_i  +  SUM_{j in FP(theta)} 150
```

Where:
- `FN(theta)` = fraud cases incorrectly predicted as genuine at threshold theta (missed fraud)
- `FP(theta)` = genuine transactions incorrectly predicted as fraud (false alarms)
- Missed fraud cost = the full transaction amount (worst-case unrecovered loss)
- False alarm cost = Rs 150 (step-up friction cost per genuinely legitimate transaction)

The asymmetry is deliberate: a single Rs 50,000 fraudulent transaction costs 333x more than a false alarm.

### 2.2 Selected Threshold

| | Value |
|---|---|
| **Operating threshold** | **0.07** |
| Validation cost at selected threshold | Rs 38,516.28 |
| Threshold search range | 0.01 to 0.99 (99 candidates, linear) |
| Selection set | Validation period (last 15% of train-period rows, chronological) |

At threshold 0.07 on the test period:
- Recall = 90.2% (captures 323 of 358 fraud cases)
- Precision = 13.4%
- The low precision reflects the cost model favouring high recall — the economics strongly prefer catching fraud over avoiding false alarms

### 2.3 Cost Curve Summary

The cost function is monotonically decreasing then increasing as threshold rises. At very low thresholds (near 0), all transactions are flagged (maximum FP cost, zero FN cost). At very high thresholds (near 1), almost no transactions are flagged (zero FP cost, maximum FN cost — all fraud missed). The optimal point (0.07) balances these extremes under the given cost parameters.

## 3. Segment Fairness Analysis (AI-3)

### 3.1 Genuine Transaction Friction Rate

Friction rate = (transactions on genuine cards where model score >= operating_threshold) / (total genuine transactions in segment)

#### By city_tier

| Segment | Friction Rate | Notes |
|---|---:|---|
| INTL | 77.10% | International cards |
| METRO | 77.03% | Metropolitan city cards |
| NON_METRO | 77.75% | Non-metro city cards |

**Parity ratio** (min/max): 0.9907
**Meets 80% parity rule**: YES (0.9907 >= 0.80)

#### By card_type

| Segment | Friction Rate | Notes |
|---|---:|---|
| CREDIT | 77.99% | Credit card holders |
| DEBIT | 77.03% | Debit card holders |

**Parity ratio** (min/max): 0.9877
**Meets 80% parity rule**: YES (0.9877 >= 0.80)

### 3.2 Disparate Impact Assessment

Both dimensions (city_tier and card_type) have parity ratios above 0.98, well above the 0.80 floor. No disparate impact is detected on the synthetic dataset.

Root cause analysis was not required (thresholds met), but the near-uniform rates are also consistent with the synthetic data generation process, which does not encode city_tier-based fraud propensity differences.

### 3.3 Mitigation Posture

Although parity is met on synthetic data, the following mitigations are documented for production deployment:

1. **Feature audit**: `distance_from_home_km` is the highest-impact feature. In real data, NON_METRO cards may have systematically higher home-to-transaction distances, inflating their friction rate. Monitor this split post-deployment.
2. **Recalibration**: If real-data parity falls below 0.80, apply isotonic regression calibration per segment or add a city_tier-conditioned post-processing step.
3. **Regular re-evaluation**: Re-run this segment report monthly with real data; FALSE_POSITIVE feedback from analysts is stored for future retraining (AI-3).

## 4. Model Features

| # | Feature | Type | Source |
|---:|---|---|---|
| 1 | `card_type` | Categorical | Card master record |
| 2 | `channel` | Categorical | Transaction |
| 3 | `mcc` | Categorical | Transaction / merchant |
| 4 | `mcc_category` | Categorical | Merchant category lookup |
| 5 | `merchant_risk` | Categorical | Merchant master record |
| 6 | `amount` | Numeric | Transaction |
| 7 | `local_hour` | Numeric | Derived from txn_ts in IST |
| 8 | `is_international` | Boolean | txn_country != home_country |
| 9 | `country_risk_high` | Boolean | Country risk lookup |
| 10 | `distance_from_home_km` | Numeric | Haversine(home_city, txn_city) |
| 11 | `velocity_10m` | Numeric | Prior txn count, 10-minute window |
| 12 | `velocity_24h` | Numeric | Prior txn count, 24-hour window |
| 13 | `amount_to_avg30_ratio` | Numeric (nullable) | amount / avg_approved_30d |
| 14 | `new_merchant_flag` | Boolean | No prior txn with merchant in 90 days |
| 15 | `card_age_days` | Numeric | txn_date - card issue_date |

**Prohibited features excluded**: `txn_id`, `txn_ts`, `city_tier`, full PAN, cardholder name, mobile number.

---

## 5. Privacy and Security

- No full PAN is stored, logged, or used as a model feature
- No cardholder name or mobile number appears in any feature or explanation
- Merchant/description free-text is never passed to the model or to LLM prompts without quoting as untrusted data
- Model explanations use aggregated SHAP values over base features only; one-hot dummy names are never surfaced to analysts

## 6. Decision Integration (AI-2)

The model score is consumed by Spring Boot with the following escalation policy:

| Rules Decision | Model Score | Final Decision | Reason Code Added |
|---|---|---|---|
| APPROVE | >= 0.70 | STEP_UP | HIGH_FRAUD_SCORE_MODEL |
| STEP_UP | >= 0.90 | BLOCK | HIGH_FRAUD_SCORE_MODEL |
| Any BLOCK | Any | BLOCK | (no change) |

If inference exceeds 150 ms or fails: fallback to rules-only decision, `model_status = MODEL_UNAVAILABLE`.
